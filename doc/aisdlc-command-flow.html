aisdlc command flow: PM to release

The commands used in a normal development flow, taken from a real test run of ticket EL-0000 (develop a login feature) in the shared repository C:\Evoke\aisdlc-demo, with its design synced from a Claude Design artifact.

57 steps. Every role starts with /aisdlc:pull and ends with /aisdlc:push and a hand-off; /aisdlc:push always pulls first, leaves merge conflicts to you, asks you to confirm the branch before pushing (the team's branch, for example S10, made by hand) and never pushes to main.

Set up Everyone, once

Per machine and repository.

# Command Run by What it does
1 git clone <repo> (or git init + git remote add origin <url>) Everyone Make the folder the shared git repository. Once
2 /aisdlc:init --role <pm|design|dev|qa> Everyone Scaffold everything for every role at once (config, tasks, designs, system, docs site, QA test scaffold); record your role locally. Once
3 cp claude.env.example claude.env Dev Set AISDLC_REPOS_ROOT to the folder holding your clones (never secrets). Once
4 /aisdlc:status-page Anyone Start the status page (http://localhost:4320): flow per ticket, documents, hand-offs. Leave it running.

PM Project manager

Requirement gathering, acceptance criteria, hand off.

# Command Run by What it does
5 /aisdlc:pull PM Latest from the other roles; shows what waits for you.
6 /aisdlc-pm:requirements EL-0000 PM Create the PM task, draft requirements.md from the ticket (or a pasted brief).
7 /aisdlc-pm:acceptance-criteria EL-0000 PM Draft numbered criteria AC1..ACn.
8 /aisdlc-pm:approve EL-0000 acceptance_criteria PM Approve the criteria; the file's hash is pinned. Human decision
9 /aisdlc-pm:jira-sync EL-0000 PM Write requirements and criteria into the Jira ticket (Jira stays optional). Optional, not run
11 /aisdlc:push PM Pull first, then commit "EL-0000: ..." and push.
12 /aisdlc:handoff EL-0000 design PM Design becomes active (UI tickets only).
13 /aisdlc:handoff EL-0000 dev PM Dev becomes active. PM can hand off to both at once.
14 /aisdlc:push PM Share the hand-off events.

Design Designer

Designs are synced from Claude Design into designs/EL-0000/.

# Command Run by What it does
15 /aisdlc:pull Designer See the hand-off from PM.
16 /aisdlc-design:sync <artifact link> --ticket EL-0000 [--pages Main] Designer Copy the prototype pages, the viewer runtime and design.md into designs/EL-0000/ after a safety scan. In the shared repo it stops before committing.
18 /aisdlc:handoff EL-0000 dev Designer Design is done; Dev has the design.
17 /aisdlc:push Designer Pull first, then commit and push the design folder.

Dev Developer

Build from tasks/EL-0000/ and designs/EL-0000/. /aisdlc-dev:feature runs the first five stage skills for you.

# Command Run by What it does
19 /aisdlc:pull Developer Get PM requirements and criteria, and the design.
20 /aisdlc-dev:add-repo <name> <path> Developer Register the application repository (once per repository). Once
21 /aisdlc-dev:feature EL-0000 Developer Dev task; reads the PM's files (no Jira fetch); drives the stages below.
jira-ticket, impact-analysis, repository-preparation (inside feature) Ticket content, impact analysis, branch EL-0000 from the latest main in the app repository.
/aisdlc-dev:design-link EL-0000 (inside feature) Read designs/EL-0000/, record snapshot v1, pin it with the source commit.
/aisdlc-dev:feature-specification EL-0000 (inside feature) Short specification with the design pin and criteria mapping.
22 /aisdlc-dev:approve EL-0000 specification Developer Approve the specification; implementation is blocked until then. Human decision
23 (implement in the application repository) Developer Code on branch EL-0000 after approval.
24 /aisdlc-dev:testing EL-0000 Developer Run tests, record validation.md.
25 /aisdlc-dev:code-review EL-0000 Developer Independent review, recorded in code-review.md.
26 /aisdlc-dev:commit EL-0000 Developer Commit "EL-0000: ..." on branch EL-0000 in the application repository.
27 /aisdlc-dev:pr EL-0000 Developer Push the branch, open the pull request in Bitbucket. Simulated in this run
28 (reviewer merges the pull request) Reviewer The merge is always a human action. Simulated in this run
29 /aisdlc-dev:pr-comments EL-0000 Developer Read, triage and fix review comments (when there are any). Optional, not run
31 /aisdlc:handoff EL-0000 qa Developer QA becomes active (after the merge).
30 /aisdlc:push Developer Share spec, design snapshot, validation, state.

QA QA engineer

Scenarios come from the PM's acceptance criteria. Tests stay local; documents are shared.

# Command Run by What it does
32 /aisdlc:pull QA See the hand-off from Dev.
33 /aisdlc-qa:test EL-0000 QA QA task from the PM's criteria, environment check, scenario drafting; continues through approval, tests and the run.
34 /aisdlc:return EL-0000 pm "<reason>" QA Gap found: no criterion for the 8-character password rule. Sends the ticket back; PM shows "changes requested". Change request
35 /aisdlc-qa:approve EL-0000 scenarios QA Approve scenarios S1-S5; hash pinned (after the loop below). Human decision
36 /aisdlc-qa:run EL-0000 QA Run the tests (a browser run); results.md. Demo: headless Chrome stood in for Playwright.
37 /aisdlc-qa:approve EL-0000 signoff QA Sign off the results: 5 of 5 pass, 0 defects. Human decision
38 /aisdlc-qa:publish EL-0000 QA Evidence and results comment on the Jira ticket (skipped in the demo). Simulated in this run
40 /aisdlc:handoff EL-0000 dev QA Dev (release) becomes active again.
39 /aisdlc:push QA Share scenarios, spec, results, state. tests/ is never committed.

Change request loop QA to PM and back

A request for changes, tracked until resolved. Runs between QA drafting scenarios and approving them.

# Command Run by What it does
41 /aisdlc:return EL-0000 pm "<reason>" QA Reason is required; adds an open item to changes.md and the status page. Change request
42 /aisdlc:pull PM PM sees 1 open change request.
43 /aisdlc-pm:refine EL-0000 PM Reopen the criteria (state back to ACCEPTANCE_CRITERIA_DEFINED).
44 (edit acceptance-criteria.md: add AC5) PM Numbers stay stable; the edit invalidates the approval.
45 /aisdlc-pm:approve EL-0000 acceptance_criteria PM Approve AC1-AC5 again. Human decision
46 /aisdlc-pm:handoff EL-0000 dev PM PM state back to HANDED_OFF_TO_DEV.
47 /aisdlc:handoff EL-0000 qa --resolve all PM Hand back to QA; refused while change requests are open unless resolved here. Change request
48 /aisdlc:push PM Share the revised criteria and the hand-off.

Release Developer (release owner)

After QA's sign-off Dev owns the release. Production deployment itself is disabled in the plugin config.

# Command Run by What it does
49 /aisdlc:pull Developer See QA's sign-off and hand-off.
50 /aisdlc-dev:post-release EL-0000 Developer Record the release (UAT merge counts as released); state RELEASED. Evidence simulated in the demo. Simulated in this run
51 /aisdlc-dev:product-knowledge-consolidation EL-0000 Developer Write the released behavior into system/product/, then clean up the dev-owned task artifacts.
52 /aisdlc-dev:finish EL-0000 Developer Dev task COMPLETED (needs the cleanup first).
53 /aisdlc:push Developer Share the consolidation, cleanup and completion.
54 (PM and QA mark their tasks COMPLETED) PM, QA State transitions; the status page shows every role done.
