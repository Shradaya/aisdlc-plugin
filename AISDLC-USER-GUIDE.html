AISDLC Plugins — User Guide

How the Project Manager, Designer, Developer and QA roles use the aisdlc Claude Code plugins to carry one ticket from a requirement all the way to production. The plugins talk to the AISDLC server, which is the shared source of truth; approvals are always made by a person in the server web UI, never by an agent.

Key concepts

A few ideas make the rest of the guide easy to follow.

  • One ticket, one flow. A ticket moves PM → (Design) → Dev → QA environment → QA → UAT → QA regression → Production. Each phase is owned by one role, and only that role can move the ticket out of it.
  • The server is the knowledge base. You push your files to it and pull other roles' files from it. Each role only pushes and pulls its own files.
  • Approvals are human-only. Gate approvals (acceptance criteria, design, specification, plan, scenarios, sign-off, regression) are made by a person in the server web UI. No plugin command and no agent can approve.
  • Automatic state sync. When you push a ticket without naming a target, the server reads your local state and moves the ticket as far as your role and the approvals allow — then stops at the next gate or hand-off and tells you why.
  • Secrets stay local. Jira and server credentials come only from environment variables. The plugins never print, store or push them.

Commands every role shares

All four plugins expose the same server commands, worded for that role. Replace <role> with pm, design, dev or qa.

SkillWhat it does
/aisdlc-<role>:initScaffold a local workspace for this role (folders, config, CLAUDE.md).
/aisdlc-<role>:serverLink the workspace to the AISDLC server, log in, and download this role's workspace files with init --project.
/aisdlc-<role>:pullFetch a ticket's files and its current phase (pull <TICKET>), or refresh workspace knowledge (pull plugin).
/aisdlc-<role>:pushSend this role's files for a ticket and let the server advance its state (push <TICKET>); push * for all; push plugin for workspace knowledge.

The developer and QA plugins also have a waiting skill — /aisdlc-dev:waiting and /aisdlc-qa:waiting — that lists the tickets currently sitting in a phase your role owns. The PM plugin has the same, /aisdlc-pm:waiting.

PM Project Manager skills

The PM turns a Jira issue into clear requirements and acceptance criteria, writes them back to Jira, and hands the ticket to design or development.

SkillWhen to use it
/aisdlc-pm:initFirst-time setup of a PM workspace.
/aisdlc-pm:serverLink the workspace to the server and log in.
/aisdlc-pm:ticket-newCreate a ticket on the server for a Jira key (PM or admin only), with a preview before it is created.
/aisdlc-pm:requirementsDraft requirements.md from the Jira issue or a pasted brief, asking you about every gap.
/aisdlc-pm:acceptance-criteriaDraft numbered acceptance criteria (AC1…ACn, Given/When/Then) from the requirements. The numbering stays stable because QA builds its scenarios from it.
/aisdlc-pm:jira-syncWrite the requirements and acceptance criteria into the Jira description, inside a marked block, after a preview, a diff and your explicit confirmation. Supports a dry run and makes a backup first.
/aisdlc-pm:push / pullSend requirements.md and acceptance-criteria.md to the server; fetch a ticket's files.
/aisdlc-pm:handoffAfter a human approves the acceptance criteria in the web UI, move the ticket to design or to development. Never approves.
/aisdlc-pm:refineHandle a ticket a developer or designer sent back, or a changed Jira issue, and revise the requirements and criteria.
/aisdlc-pm:waitingShow the tickets waiting on the PM.

Design Designer skills

The designer authors a UI/UX prototype for a design ticket and hands the approved design to development. The design block is optional; a ticket can skip straight to development.

SkillWhen to use it
/aisdlc-design:initSet up a design workspace, including the preview web app.
/aisdlc-design:serverLink to the server and log in.
/aisdlc-design:designAuthor the prototype (HTML/CSS directly, or Claude Design then export), produce design.md plus a self-contained prototype, version and hash it, and run the designer's review.
/aisdlc-design:commitCommit the approved design to the design repository and guide the push so developers can consume it.
/aisdlc-design:push / pullSend the ticket's design files to the server; fetch the requirements and acceptance criteria the PM wrote.

Dev Developer skills

The largest plugin. The core path is feature; the rest are the individual stages and the specialised workflows. Only the skills a user runs directly are listed as commands; many are stages the feature workflow calls for you.

Start and overview

/aisdlc-dev:status / :status-pageRead-only local overview of tasks, repositories and approvals. (The server web UI now shows the same lifecycle, approvals and documents.)

/aisdlc-dev:resumeResume an interrupted or failed task from the first safe state.

The whole journey

One ticket, from a requirement to production, with the skills each role runs at each step. Approvals happen in the server web UI between the steps.

PM → (Design) → Dev → release to QA env → QA → release to UAT → QA regression → production

PM 1. Requirements & acceptance criteria

Server phases: REQUIREMENT_GATHERING → ACCEPTANCE_CRITERIA_DEFINED
  1. Create the ticket for the Jira key — /aisdlc-pm:ticket-new.
  2. Draft the requirements — /aisdlc-pm:requirements.
  3. Draft the numbered acceptance criteria — /aisdlc-pm:acceptance-criteria.
  4. Write them back into the Jira description — /aisdlc-pm:jira-sync.
  5. Send them to the server — /aisdlc-pm:push <TICKET>.
  6. A person approves the acceptance criteria in the web UI.
  7. Hand off to design or development — /aisdlc-pm:handoff.

Design 2. Prototype (optional)

Server phases: DESIGN_BRIEF → … → DESIGN_COMMITTED, then back to TICKET_READY for dev
  1. Fetch the requirements and acceptance criteria — /aisdlc-design:pull <TICKET>.
  2. Author the prototype and design.md — /aisdlc-design:design.
  3. A person approves the design in the web UI.
  4. Commit and hand off the approved design — /aisdlc-design:commit, then /aisdlc-design:push <TICKET>. The ticket returns to development as TICKET_READY.

Dev 3. Build and release to the QA environment

Server phases: TICKET_READY → … → PR_CREATED → RELEASED_TO_QA
  1. Pick up the ticket — /aisdlc-dev:waiting, then /aisdlc-dev:pull <TICKET> to get the requirements, criteria and design.
  2. Run the feature workflow — /aisdlc-dev:feature. It walks through impact analysis, the specification (with a human approval gate), implementation, tests, review and the commit.
  3. Open the pull requests — /aisdlc-dev:create-pr (use /aisdlc-dev:promote if a branch won't merge cleanly).
  4. Release to the QA environment once the PR is merged into lf-qa — /aisdlc-dev:release qa. This moves the ticket to RELEASED_TO_QA and hands it to QA.

QA 4. Test in the QA environment

Server phases: ENVIRONMENT_READY → … → QA_COMMITTED
  1. Pick up the ticket — /aisdlc-qa:waiting, then /aisdlc-qa:pull <TICKET> for the acceptance criteria.
  2. Run the QA workflow — /aisdlc-qa:test. It drafts scenarios from the criteria for you to approve, generates Playwright tests, and runs them with /aisdlc-qa:run.
  3. A person approves the scenarios and, at the end, signs off the results in the web UI.
  4. Publish evidence to Jira — /aisdlc-qa:publish — and commit the tests to the regression suite — /aisdlc-qa:commit.
  5. Send QA's files to the server — /aisdlc-qa:push <TICKET>. QA passing hands the ticket back to dev as QA_PASSED.

Dev QA 5. Release to UAT & regression

Server phases: QA_PASSED → RELEASED_TO_UAT → QA_REGRESSION → REGRESSION_PASSED
  1. Dev releases to UAT once the PR is merged into lf-uat — /aisdlc-dev:release uat. The ticket becomes RELEASED_TO_UAT and goes to QA.
  2. QA runs the regression suite on UAT — /aisdlc-qa:run against the uat environment — and produces regression-results.md, then /aisdlc-qa:push <TICKET>.
  3. A person approves the regression in the web UI. The ticket becomes REGRESSION_PASSED and returns to dev.

Dev 6. Production & close-out

Server phases: REGRESSION_PASSED → PROD_RELEASE → KNOWLEDGE_CONSOLIDATED → COMPLETED
  1. Release to production — /aisdlc-dev:release prod.
  2. Bring main back into the environment branches — /aisdlc-dev:sync-main.
  3. Verify the release and consolidate the knowledge — /aisdlc-dev:post-release (which runs product-knowledge-consolidation).
  4. Close the ticket — /aisdlc-dev:finish.

The defect loop

If QA finds a defect in the QA environment (phase AWAITING_DEV_FIX) or the UAT regression fails, the ticket goes back to the developer. The developer runs /aisdlc-dev:fix-defect to return the task to implementation, fix it with a regression test, re-open the PR to the same environment branch and hand it back to QA with /aisdlc-dev:release qa (or uat). QA re-verifies with /aisdlc-qa:run.
Approvals are never automated. Every gate — acceptance criteria, design, specification, plan, scenarios, results sign-off, regression — is approved by a person in the server web UI. When you push a ticket, the server advances it only as far as the approved gates allow and then stops, telling you which approval it is waiting on.
