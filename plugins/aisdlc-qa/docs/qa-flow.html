aisdlc-qa flow

How the QA plugin takes one Jira ticket from acceptance criteria to approved scenarios, to Playwright tests you watch run, through the defect loop with the developer, to signed-off evidence on the ticket and tests in the regression suite.

One command drives the whole thing: /aisdlc-qa:test <TICKET>. It is resumable: run it again at any point and it picks up from the ticket's current state. Claude does the drafting, generating and running; the QA engineer makes every decision that matters, and the plugin's hooks and state engine refuse anything that skips a decision.

The flow

Claude does it QA decides Hard gate (hash-pinned approval) Developer Done - - - loop back

Checkpoints

# Checkpoint Who What happens Leaves behind
1 Ticket loaded Claude Fetches the Jira ticket and numbers its acceptance criteria AC1…ACn. If Jira is unreachable, asks you for the details rather than guessing. tasks/<T>/jira.md (hashed)
2 Environment ready Claude QA Picks the environment (qa/uat), refuses production hosts, checks it is reachable, signs in once and saves the session. You confirm the environment, the build under test and that the data is synthetic. environment in task state, .auth/<env>.json
3 Scenarios drafted Claude The scenario-writer agent turns the ACs into scenarios. Optionally the Playwright planner explores the live app to make steps concrete. Expected results come only from the ticket; where the app disagrees, that is an open question. tasks/<T>/scenarios.md
4 Scenario approval QA You see the scenario ↔ AC table and open questions, then approve, ask for changes or reject. Approval is pinned to the file's hash: editing it afterwards cancels the approval. approvals.scenarios
5 Tests generated Claude Copies the approved scenarios to spec.md. The Playwright generator runs each step live in a visible browser and writes one test per scenario. qa-test-reviewer checks coverage and quality. tests/<T>/s<n>-*.spec.ts, tasks/<T>/spec.md
6 Run, QA watches Claude Runs the ticket's tests headed and slowed down (or in UI mode). Every step gets a screenshot; trace and HTML report are kept per run. tasks/<T>/evidence/run-<N>/
7 Failure triage QA results-analyst suggests a cause for each failure; you decide: app defect → 7a, test issue → the healer fixes the test (never by loosening an assertion) and you review the diff, env/data → re-run. tasks/<T>/results.md
7a Defect on Jira Claude QA Claude drafts one comment for all defects in the run: scenario, AC, steps, expected vs actual, environment, build, failure screenshots. You preview it and choose post, edit or don't post. defects.D<k> (open), Jira comment
7b Wait for developer Developer The task stops. /aisdlc-qa:status or resuming test shows developer replies and status changes since the defect comment. —
7c Re-verify the fix QA Claude You confirm the fix is deployed and give the new build. /aisdlc-qa:run <T> runs the failing scenarios first, then the full ticket suite. Fixed defects get a "verified fixed on build X" reply once you confirm. defects.D<k> fixed, new run
8 Results sign-off QA Allowed only when every scenario passes or each defect is fixed or explicitly waived with a reason. You review results.md and the report, then sign off, re-run or reject. Pinned to the hash of results.md. approvals.signoff
9 Evidence to Jira Claude QA /aisdlc-qa:publish uploads screenshots and the report zip and posts the results comment, after you confirm. Re-publishing doesn't duplicate attachments. Jira attachments + comment
10 Commit tests Claude QA /aisdlc-qa:commit stages tests/<T>/ and tasks/<T>/spec.md only, and commits <T>: <summary> on branch <T>. commit on branch <T>
11 Done QA You push and open the PR; once merged the tests are part of the regression suite. —

Decisions you make

Scenario approval (4)

Does every AC have a scenario, are the expected results the ticket's, are the open questions answered?

Approve · Request changes · Reject task

Triage (7)

For each failure: is it the app, the test, or the environment?

App defect · Test issue (heal) · Env/data (re-run)

Defect comment (7a)

Nothing is posted to Jira until you have seen the exact comment and screenshots.

Post · Edit · Don't post

Results sign-off (8)

Every scenario passed, or each remaining defect is waived with a reason you give.

Sign off · Re-run · Reject

You also confirm the environment and build (2), that the developer's fix is deployed (7c), publishing to Jira (9) and the commit (10).

Commands

Command Use it to
/aisdlc-qa:init Scaffold the QA workspace (the Playwright test repo), install Playwright and its test agents. Offers --migrate-layout for older workspaces.
/aisdlc-qa:test <T> Drive checkpoints 1–8; resumable from any state.
/aisdlc-qa:run <T> Re-run at any test stage, e.g. on a new build. --ui, --headless, --only S1,S3, --video.
/aisdlc-qa:publish <T> Attach the signed-off evidence to Jira (9).
/aisdlc-qa:commit <T> Commit the ticket's tests and spec (10), then mark complete once pushed (11).
/aisdlc-qa:status Where every ticket stands, including developer replies on open defects.
/aisdlc-qa:add-env <name> <url> Add a test environment, or block a production host.
/aisdlc-qa:check "<what>" A quick check without a ticket; stays in checks/, never in Jira or the suite.

What is enforced, not just advised

  • No tests without approved scenarios. The hook blocks writes to tests/<T>/ and tasks/<T>/spec.md unless the scenarios are approved and unchanged since; this covers Write/Edit, shell writes and the Playwright generator.
  • One folder per ticket. A file in tests/<T>/ that names another ticket is blocked. spec.md can only be an exact copy of the approved scenarios.md.
  • No sign-off with open defects. The state engine refuses it; waiving needs your choice and a reason.
  • Healing never weakens a test. A loosened assertion or changed expected value is a scenario change and needs re-approval.
  • Never production. Environments must allow automation, and blocked or production-looking hosts are refused by the runner, the hook and the Playwright config. Data is synthetic.
  • Credentials stay out of reach. QA_USERNAME/QA_PASSWORD and JIRA_* are environment variables (QA login may be in the workspace .env). Claude can't read .env or .auth/; secrets are never printed, logged, committed or in evidence.
  • Jira writes only on your say-so, only through jira-attach.js, only when switched on in config/integrations.yaml, and final evidence only after sign-off.
  • State only through the state CLI; task.yaml is never edited by hand.

Where things live

tests/
  auth.setup.ts            sign in once, session reused
  seed.spec.ts             starting page for the Playwright agents
  <T>/
    s1-<scenario>.spec.ts  one test per scenario, tagged @<T> @<T>-S1 @<T>-AC1
    helpers.ts             this ticket's own helpers (optional)
fixtures/                  qa.ts (qaStep + screenshots), env.ts, pdf.ts, cross-ticket helpers
tasks/<T>/
  spec.md                  approved scenarios — the only committed file here
  jira.md  scenarios.md  results.md  task.yaml
  evidence/run-<N>/        screenshots/, report/, traces, results.json
checks/                    ad-hoc checks (gitignored)
config/                    environments.yaml, integrations.yaml, workspace.yaml

Run one ticket by hand with npx playwright test tests/<T>; npx playwright test runs the whole regression suite. Per-step screenshots are the proof; video only when you ask for it.
